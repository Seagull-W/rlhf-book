# policy_gradients 训练代码梳理

本文基于当前目录源码整理，重点回答：训练如何启动、样本如何生成、奖励如何转成优势、loss 如何产生梯度，以及参数何时更新。描述的是**本仓库的实际实现**，不保证与同名算法论文的完整方案一致。未运行模型训练，也不引用 README 中的参考实验作为本机验证结果。

## 1. 先建立整体认识

这是一套共享训练骨架的语言模型策略梯度教学实现：

```text
YAML → Config → 程序化题目数据集
                ↓
初始化 policy / 可选 reference / PPO value model
                ↓
RolloutEngine：取题 → 同题生成 K 个回答
                ↓
环境判分 + 格式奖励 + 可选长度惩罚
                ↓
记录旧策略 log probability / 参考 log probability / 旧 value
                ↓
可选 reward KL → 计算同题组优势或 GAE → 可选 DAPO 过滤
                ↓
Experience 移到 CPU → 拆成单回答 → 填入当前 ReplayBuffer
                ↓
打乱回答 → 拼成训练 microbatch → 当前模型重新前向
                ↓
算法 loss → backward → 梯度累积 → 裁剪 → Adam.step()
                ↓
清空当前阶段梯度，使用更新后的策略采集下一批
```

这里不是“从固定答案数据集读 labels 做交叉熵”，而是“模型自己生成答案，由环境给奖励，再用奖励加权的概率目标更新模型”。默认任务是 `reasoning_gym` 的 `spell_backward`，不加载人类偏好数据或学习式 reward model。

## 3. 初始化：训练开始前具体做什么

### 3.1 参数与设备

`main_cli()` 仅支持必需参数 `--config` 和可选参数 `--device auto/cuda/cpu`。YAML 经 `yaml.safe_load` 传给 `Config(**raw)`，遗漏字段用 `Config` 默认值补齐。

`main()` 首先设置 Python、NumPy、PyTorch 随机种子，然后解析设备。`auto` 有 CUDA 则使用 CUDA，否则 CPU；显式要求 CUDA 而不可用时会报错。CUDA 下 policy、reference、value 分别使用 `model_device_id`、`ref_model_device_id`、`val_model_device_id` 指定的卡。

注意：设备编号是在选择 CUDA 后才生效；这不是 DDP 或张量并行，每个模型整体放到一个指定设备。

### 3.2 数据与模型

- `create_dataset()` 把 `data.specs` 转为 reasoning-gym 的 `DatasetSpec`，构建 `composite` 数据集；`size` 是题目数量，不是生成回答数量，`weight` 用于任务混合。
- `load_model()` 加载 tokenizer 和 `AutoModelForCausalLM`，使用 BF16、`trust_remote_code=False`，默认开启 non-reentrant gradient checkpointing。
- attention 选择函数仅在 `platform.machine() == "x86_64"` 且能导入 `flash_attn` 时选择 `flash_attention_2`；其他情况选择 `sdpa`。不要理解为任意 x86 Windows 环境都会启用 Flash Attention。
- `beta` 非零时加载初始模型作为 reference；默认配置 `beta=0`，不加载 reference。
- 只有 PPO 加载额外 value model：也是完整 causal LM，但把 `lm_head` 替换为输出维度 1 的无 bias 线性层。不是在 policy 上附加共享 value head。
- optimizer 是 `torch.optim.Adam`，不是 AdamW；参数包含 policy 的全部参数，以及 PPO 的全部 value 参数，没有 LoRA、量化或冻结 backbone。

reference 虽然没有显式 `requires_grad_(False)`，但采样在 `no_grad` 内，且 reference 不加入 optimizer，所以当前流程不更新它。

## 4. Rollout：一批经验是如何生成的

### 4.1 外层题目遍历与 buffer 填充

`RolloutEngine` 内部题目 DataLoader 使用 `batch_size=prompts_per_step`、`shuffle=True`、`drop_last=True`。但 `_iter_entries()` 会把 DataLoader 的 batch 再逐条展开。

因此实际生成不是“同时批处理多个不同题目”，而是：**逐题调用 generate，一次生成同一个题目的 K 个回答**，其中 `K=num_rollouts`。

`_step()` 的目标 buffer 长度为：

```text
expected = prompts_per_step × num_rollouts
```

每次加入完整题目组。普通算法通常收集 `prompts_per_step` 道题；DAPO 会丢弃某些题目组，所以可能消耗更多题目才能填满。数据耗尽时可以返回非满 buffer；空 buffer 才使迭代结束。

整个 `main()` 只遍历这个题目流一次，没有配置训练 epoch、最大 optimizer steps 或对同一 buffer 重复多轮训练。

### 4.2 构造提示和生成

`_generate_experience(entry)` 的主要顺序：

1. 把同一 `entry` 复制 K 次。
2. 用 `SYSTEM_PROMPTS["DeepSeekZero"]` 作为 system prompt，题目的 `question` 作为 user 内容。
3. 用 `apply_chat_template(..., add_generation_prompt=True, enable_thinking=True)` 转成字符串。
4. tokenizer 左 padding，构建 prompt 的 input IDs 和 attention mask。
5. `model.generate()` 用 `do_sample=True` 和配置中的 temperature、top-p、top-k、min-p、`max_new_tokens` 采样。
6. 从 prompt 宽度之后切出 completion，decode 后用于判分。

输出保留完整的 `prompt + completion` token 序列，后续重新前向时依然输入完整上下文。`max_new_tokens` 只限制生成长度，不是完整序列长度。

### 4.3 为什么需要两个 mask

- `attention_mask`：完整序列中 token ID 不等于 pad ID 的位置，用于模型前向。
- `action_mask`：只标记新生成且不是 pad 的 token，决定哪些位置计入 RL loss。

生成后 `action_mask = action_mask[:, 1:]`，这是为了匹配 next-token prediction 的一位移位：位置 t 的模型输出预测序列位置 t+1。

因此模型仍然读取 prompt，但 prompt token 本身不直接计入策略损失。

## 5. 张量形状与 next-token 对齐

记 K 为每题回答数，B 为训练 microbatch 中回答数，T 为当前 batch 补齐后的完整序列长度。

| Experience 字段 | 生成时组内形状 | 训练时形状 | 含义 |
|---|---|---|---|
| `sequence_ids` | `[K,T]` | `[B,T]` | prompt + completion |
| `attention_mask` | `[K,T]` | `[B,T]` | 模型有效输入位置 |
| `action_mask` | `[K,T-1]` | `[B,T-1]` | 参与 loss 的生成目标 |
| `log_probs_old` | `[K,T-1]` | `[B,T-1]` | 采样时策略对实际 token 的 log probability |
| `log_probs_ref` | `[K,T-1]` 或 None | `[B,T-1]` 或 None | 固定 reference 的 token 概率 |
| `values_old` | `[K,T-1]` 或 None | `[B,T-1]` 或 None | PPO 旧 value |
| 各奖励分量 | `[K,1]` | `[B,1]` | 每条回答一个分数 |
| 非 PPO `advantages` | `[K,1]` | `[B,1]` | 序列级优势，广播到所有生成 token |
| PPO `advantages` | `[K,T-1]` | `[B,T-1]` | GAE token 级优势 |

`compute_log_probs()` 的核心实现是：

```python
logits = output.logits[:, :-1, :].to(torch.float32)
log_probs = F.log_softmax(logits, dim=-1)
targets = sequence_ids[:, 1:].unsqueeze(-1)
target_log_probs = torch.gather(log_probs, dim=-1, index=targets).squeeze(-1)
```

这里只提取已经生成的那个 token 的 log probability，不是保留全部词表概率用于 loss，也不是直接调用模型内置的 labels loss。模型参数/前向使用 BF16，概率计算转 FP32。

## 6. Reward：没有 reward model，如何判分

`compute_rewards()` 返回包含五个键的 TensorDict：

| 键 | 实际计算 |
|---|---|
| `correctness` | `extract_answer(completion)` 后调用 `dataset.score_answer(answer, entry)` |
| `format` | `<think>`、`</think>`、`<answer>`、`</answer>` 每种存在一次加 0.25 |
| `penalty` | 仅 DAPO 计算超长惩罚；其他算法为 0 |
| `total` | `correctness + penalty + format_weight * format` |
| `binary` | `correctness * (format == 1.0)` |

`format_weight` 默认 0.5；例如 correctness=1、format=1、penalty=0 时 total=1.5。因此 total 不等于正确率。

格式奖励只是检测标签是否存在，不校验先后顺序、严格嵌套、数量或标签内容；`<think>` 如果已经在 prompt 模板中，而没有出现在解码出的 completion 中，也不会获得该项分数。

`binary` 的名字容易造成误解：代码没有判断 `correctness == 1`，只要求 format=1，再乘 correctness。若某任务给 correctness=0.5，则 binary 也可为 0.5；只有 correctness 本身为 0/1 时它才是真正二值。

DAPO 长度惩罚设 `safe_len = l_max-l_cache`：

```text
length <= safe_len          → 0
safe_len < length <= l_max  → (safe_len-length)/l_cache
length > l_max              → -1
```

当前 DAPO YAML 是 `l_cache=128`、`l_max=512`，所以前 384 个有效 action token 不罚，之后线性下降到 -1。长度来自 `action_mask.sum()`，不是字符串字符数。

## 7. Advantage：算法差异首先发生在这里

除 PPO 外，优势在**每一个题目的 K 个回答之间**计算；不是把整个 rollout buffer 的所有题目混在一起计算均值。优势算完后才拆开组、打乱训练，所以训练 microbatch 不必保持完整题目组。

记组内奖励为 R，均值为 mean(R)，标准差为 std(R)：

| 算法 | 当前实现的优势 |
|---|---|
| REINFORCE | `A=total`，没有 baseline |
| RLOO | `A=K/(K-1) * (total-mean(total))`，等价于减去其他回答的平均奖励 |
| GRPO、GSPO、CISPO、SAPO、DAPO | `A=(total-mean(total))/(std(total)+1e-8)` |
| DrGRPO | `A=total-mean(total)`，不除标准差 |
| MaxRL | 令 q=mean(binary)，q>0 时 `A=(binary-q)/q`，否则全零 |
| PPO | 把序列奖励放在最后有效 action 位置，用旧 value 计算 GAE |

标准差调用的是 PyTorch `std` 的默认行为，没有显式使用总体标准差。组标准化算法必须避免 `K=1`（可能出现 NaN）；RLOO 的 K=1 会除零。配置模型目前没有强制检查这些约束。

例：GRPO 同题奖励 `[0,0,1,1]`，均值 0.5，默认样本标准差约 0.577，优势约 `[-0.866,-0.866,0.866,0.866]`。每个回答的该标量会广播给自身全部有效生成 token。

### PPO 的 GAE 写法

`compute_gae()` 找到每条回答最后一个有效 action，构造终止标记；终点之后不 bootstrap，再从右往左循环：

```text
delta_t = reward_t + not_done_t * gamma * next_value - value_t
A_t     = delta_t + not_done_t * gamma * lam * running_advantage
```

最终乘 action mask 排除 prompt 与 padding。训练时 value target 是 `returns = advantages + values_old`，不是重新从当前 value 算优势。PPO YAML 覆盖默认值为 `gamma=1.0`、`lam=0.98`、`vf_coef=0.5`、`clip_eps_val=0.4`。

## 8. KL：在哪个阶段加，reference 与 old 有何区别

- `old` 是**当前这批 rollout 采样时**的策略概率；不会随这批数据的 optimizer 更新变化。
- `reference` 是初始化时另外加载的模型；它跨 rollout 保持固定，用于限制策略偏离初始模型。
- `current` 是训练前向时的策略概率，有梯度，也会随更新改变。

`loss.py` 支持：

```text
kl1 = log_pi - log_ref
kl2 = (log_pi-log_ref)^2 / 2
kl3 = expm1(log_ref-log_pi) - (log_ref-log_pi)
```

mask 在估计函数里先作用于 log ratio；`kl3` 使用 `expm1` 避免接近零时的消减误差，但没有额外的大指数溢出保护。单样本的 kl1 可能为负，不能把它当作逐 token 必然非负的精确 KL。

| 算法 | `beta` 非零时的实际作用位置 |
|---|---|
| REINFORCE、RLOO、PPO | rollout 阶段先算 old/reference 的回答内平均 KL，从 total reward 减去 `beta * KL`，再算优势 |
| GRPO、DrGRPO、GSPO、CISPO、SAPO | 训练 loss 加 `beta * KL(current, reference)` |
| DAPO、MaxRL | 当前 reward 和 loss 路径均不应用 KL |

所以 PPO 并不是在 `PPOLoss` 中额外加 KL；它通过已经改变的 reward/GAE 接收 KL 信号。DAPO 或 MaxRL 若设置非零 beta，仍会触发 reference 加载和概率计算，却没有对应的 KL 训练效果。

## 9. Buffer：为什么可以打乱、为什么移到 CPU

采样在 `torch.no_grad()` 下完成，旧概率、奖励、优势和旧 value 都是固定训练目标，不携带 rollout 计算图。

组 Experience 先 `.to(cpu)`，再由 `ReplayBuffer.add()` 拆成单回答。训练 DataLoader 使用 `join_experiences_batch()` 左补齐后堆叠；普通张量用零补齐（token ID 也是 0），新增位置的两个 mask 为假，奖励 TensorDict 直接 stack。

这减少了 buffer 占用的 GPU 内存，并允许不同题目的不同长度回答组成训练 microbatch。训练每次取出的 exp 再移动到 policy 设备；PPO 当前 value 前向发生在 value 设备，其输出随后移回 policy 设备计算 loss。

虽然叫 ReplayBuffer，它只是本轮 rollout 的临时容器，不是长期经验回放池。每次 `_step()` 新建 buffer，训练后不跨轮复用旧经验。

## 10. Loss：共享骨架与十种算法的区别

令 `ratio=exp(log_probs_current-log_probs_old)`，`A` 为固定优势，`clip(ratio)` 的区间为 `[1-clip_eps_lo,1+clip_eps_hi]`。

### 10.1 GRPO / DrGRPO / PPO 的策略部分

```text
policy_loss_token = -min(ratio*A, clip(ratio)*A)
```

min 是逐元素计算，不是简单“ratio 越界所有梯度都截断”。A 正负不同，起作用的分支也不同。负号是把要最大化的奖励目标转换为最小化 loss。

GRPO 与 DrGRPO 共用 `GRPOLoss`。**当前 DrGRPO 只修改优势，不改长度归一化**：仍然先每个回答对 token 取平均，再对 batch 取平均；不能据此说它完整实现了同名算法的所有去偏设计。

PPO 再添加 value loss：

```text
returns = A + values_old
values_clipped = clamp(values_current, values_old-eps_val, values_old+eps_val)
value_loss_token = max(0.5*(returns-values_current)^2,
                       0.5*(returns-values_clipped)^2)
loss_token = policy_loss_token + vf_coef*value_loss_token
```

value 和 policy 参数由同一个 optimizer 更新，梯度裁剪也针对两者合并后的参数列表。

### 10.2 其他算法

| 算法 | 实际 loss 核心 | 需要特别理解的点 |
|---|---|---|
| REINFORCE / RLOO | `-log_probs_current*A` | 共用 ReinforceLoss；RLOO 的差异在优势 |
| MaxRL | `-log_probs_current*A` | 用 MaxRL 优势，不使用 ratio clipping |
| GSPO | `sequence_ratio=exp(masked_mean(log_current-log_old))` 后做 clipped surrogate | 是 token ratio 的几何平均，不是直接使用整条序列概率比的乘积 |
| CISPO | `-stop_gradient(clip(ratio))*A*log_probs_current` | ratio/clipping 在 no_grad 下，只对 log probability 求导 |
| SAPO | `-A * 4/temp * sigmoid(temp*(ratio-1))` | A>0 用 temp_pos，否则 temp_neg；平滑门没有 detach |
| DAPO | clipped surrogate，再除整个 microbatch 的有效 token 总数 | 不先逐回答取平均，不加 KL |

除了 DAPO，这些类最终都使用 `masked_mean(loss, action_mask, dim=-1).mean(dim=0)`：每个回答等权，回答内部按有效 token 平均。DAPO 则更长回答包含更多 token，权重随 token 数变化。

注意 DAPO 的归一化范围是**单个训练 microbatch**；再做等权梯度累积不一定等价于把累积窗口的全部 token 放在一起归一化。

### 10.3 梯度到底从哪里来

generate 不需要可导。固定采样得到的 token 后，训练阶段重新前向得到可导的 `log_probs_current`，loss 用固定的奖励/优势加权这些概率，这个新的前向图才负责更新 policy。

GRPO 若一整组回答奖励一样，组内优势全零；beta=0 时该组没有策略学习信号。零数值 loss 也不一定代表零梯度：标准化优势在 ratio=1 时可能正负抵消，但每条回答的 log probability 对参数的梯度不同。

## 11. DAPO 动态过滤：是补采样，不是只删除样本

`_dapo_filter()` 查看**原始 correctness**：同题所有回答都等于 `accuracy_min_reward` 或都等于 `accuracy_max_reward` 时，整个组丢弃。

然后 `_step()` 继续取下一道题，直到满足期望回答数或题目耗尽。过滤不依据 total，因此即使格式奖励或长度惩罚不同，原始 correctness 全 0/全 1 的组也会丢弃。

它并非泛化的“剔除所有零方差组”：如果 correctness 全部相同但不是配置的两端值，组仍保留。若最后所有题目都被过滤，会返回空 buffer 并结束训练。

## 12. train.py：反向传播和更新的精确节奏

每拿到一个 replay buffer，`main()` 会：

1. 对 buffer 记录五种 `avg_*` reward 和经过的 `hours`。
2. policy / value 切回 `train()`。
3. 创建回答级 DataLoader：`batch_size=train_batch_size`、打乱、`drop_last=True`。
4. 开始前 `optimizer.zero_grad(set_to_none=True)`。
5. 每个 microbatch 重新算 current log probability 和 PPO current value。
6. 计算 loss；非有限 loss 直接跳过。
7. `(loss / batch_acc).backward()`，累计未缩放 loss 用于日志。
8. 达到 `batch_acc` 个索引位置，或到达最后一个 microbatch 时，裁剪梯度、`optimizer.step()`、清梯度并记录 loss/grad_norm。

默认 GRPO 的具体算例：

```text
prompts_per_step=4，num_rollouts=8
→ 每轮采样 4 道题、32 个回答
train_batch_size=2
→ 16 个训练 microbatch
batch_acc=4
→ 每次更新通常使用 8 个回答，当前 buffer 更新 4 次
data.size=3000
→ 无过滤时 750 轮 rollout，共 3000 次 optimizer 更新
```

这里“rollout 一轮”和“optimizer step 一次”不是同一概念；W&B 在两种时点分别 log，默认 W&B step 也不能直接视为 optimizer step。

假设全部 loss 有限且无过滤：题目可用数为 `floor(data.size/prompts_per_step)*prompts_per_step`；每个 buffer 的训练 microbatch 数是 `floor(len(buffer)/train_batch_size)`，optimizer 更新次数是 `ceil(microbatch数/batch_acc)`。

### 实施时要留意的边界行为

- 题目和训练 DataLoader 都有 `drop_last=True`：不足题目 batch 的尾部题目、不足训练 batch 的尾部回答都会丢弃。
- 最后一个累积窗口不足 `batch_acc` 时仍然按配置值缩放 loss，因此最后一次更新的梯度可能偏小。
- 非有限 loss 的跳过逻辑按原始 `idx` 决定更新边界，不是按成功 backward 次数；日志的平均 loss 分母也不一定等于成功累积次数。如果最后一个 microbatch 被跳过，残留梯度可能到下轮初始化时被清掉而没有 step。
- rollout 使用 `eval()`，训练使用 `train()`；若模型含 dropout，即使参数没变，两阶段重算概率也可能不一致。
- generate 使用 temperature/top-k/top-p 等改变采样分布；`compute_log_probs()` 重算的是原始模型分布，没有应用这些采样变换，old 并非严格的“经过采样变换后的行为分布概率”。
- pad ID 未定义时复用 EOS ID，mask 会同时排除 EOS；代码不是通过“找到首个 EOS”单独定义结束边界。

## 13. 配置速查：哪些参数真正控制什么

所有随附配置使用 `Qwen/Qwen3-1.7B` 和单一 `spell_backward` 任务（单词长度 3～10），学习率 5e-6，最大生成 512，train batch=2，梯度累积=4，seed=42，默认 KL 关闭。

| YAML / 算法 | 题目数 | prompts_per_step | K | 关键差异 |
|---|---:|---:|---:|---|
| reinforce | 15000 | 8 | 1 | 原始 reward 优势 |
| rloo | 1000 | 4 | 8 | leave-one-out baseline |
| ppo | 10000 | 16 | 1 | 单独 value model + GAE |
| grpo | 3000 | 4 | 8 | clip 下/上均 0.2 |
| drgrpo | 1000 | 4 | 8 | 不做优势标准差归一化 |
| gspo | 1000 | 4 | 8 | 序列级几何平均 ratio |
| cispo | 1000 | 4 | 8 | clip 下 0.2、上 0.4；ratio 停止梯度 |
| sapo | 3000 | 4 | 8 | 正/负优势温度 1.0 / 1.05 |
| dapo | 3000 | 4 | 8 | clip 下 0.2、上 0.28；动态过滤、长度惩罚 |
| maxrl | 3000 | 4 | 8 | 用 binary 字段计算相对成功优势 |

配置模型目前只额外验证 `kl_estimator`；`loss` 是普通字符串，其他数值约束并不完整。组算法要自行确保 K>1、batch 参数为正、DAPO 的 `l_cache>0` 且长度阈值合理。

## 14. 启动与小规模实施

在项目 `code` 根目录运行，而不是进入 `policy_gradients` 后直接执行 `train.py`（后者会影响相对导入）。以下为供手动执行的命令，本文未启动训练：

```powershell
uv sync
uv run python -m policy_gradients.train --config policy_gradients/configs/grpo.yaml
```

CPU 路径可显式选择：

```powershell
uv run python -m policy_gradients.train --config policy_gradients/configs/grpo.yaml --device cpu
```

这只是设备选择，不保证任意 CPU 的 BF16 运算支持和可接受训练速度。Windows 的 CUDA wheel 来源不由项目的 Linux 专用 index 规则覆盖，需检查实际安装的 PyTorch 是否支持 CUDA。

做冒烟实验时，复制 YAML 为本地小配置，不要覆写参考配置。一个保持 GRPO 组对比和完整累积窗口的设置示例：

```yaml
data:
  size: 8
  specs:
    - name: spell_backward
      weight: 1
      config:
        min_word_len: 3
        max_word_len: 5
loss: grpo
model_name: Qwen/Qwen3-1.7B
prompts_per_step: 2
num_rollouts: 4
train_batch_size: 2
batch_acc: 4
max_new_tokens: 128
beta: 0.0
wandb_project: null
```

保存后用 `--config` 指向新文件。其余字段取 Config 默认值。这个示例用于检查流程，不是效果保证；缩短生成可能导致格式不全或奖励无差异，必须查看实际 completion。正式长训练应后台启动、持续检查日志，且未检查可用显存前不要并行跑多个任务。

### 日志与结果检查

- W&B 的 entity/project/run name 可被同名 `WANDB_*` 环境变量覆盖；YAML 的 `wandb_project: null` 只在没有 project 环境变量覆盖时关闭日志。不要把 PowerShell 空字符串当作 YAML null。
- `avg_correctness` 是训练采样回答的环境平均分，不是 held-out accuracy。
- `avg_format` 看格式是否齐全；`avg_total` 看含格式/长度/KL shaping 的总奖励；`avg_binary` 要结合任务是否二值判分理解。
- `loss`、`grad_norm` 在 optimizer 更新时记录；`grad_norm` 来自 `clip_grad_norm_` 的返回值，即裁剪前的总范数。
- Rich 终端打印奖励均值与一个回答。展示样本由最后一次生成记录决定，DAPO 下可能来自后来被过滤的组，不一定属于最终 buffer。
- 若组奖励始终一致，应先检查任务难度、抽样数量、生成完整性和奖励函数，而不是只盯 loss 曲线。

## 15. 这套实现已有和没有的工程功能

已有：配置驱动、任务混合、随机种子、CUDA/CPU 选择、梯度检查点、CPU 经验缓存、梯度累积、梯度裁剪、可选 KL、PPO value model、DAPO 补采样、W&B 和终端日志。

当前没有：模型 checkpoint/final export、optimizer 保存与恢复、独立验证集评估、学习率 scheduler、DDP/FSDP、LoRA、vLLM/异步 rollout、多 epoch buffer 重用、统一显存规划。训练结束后不会自动在目录里得到可加载的微调模型。

若要扩成完整训练项目，应优先补保存/恢复、固定评估题目和有效更新计数，再按需要补分布式与高吞吐生成；这些是后续实施方向，不是本次已修改的功能。

`scripts/run_all_policy_gradients.sh` 虽然名字叫 run_all，实际只依次运行 RLOO、PPO、DrGRPO、GSPO、CISPO、SAPO，不包含 GRPO、REINFORCE、DAPO、MaxRL，也不是 Windows PowerShell 脚本。

## 16. 快速复述一遍训练逻辑

1. 同题采样多个回答，为每个回答保存完整 token 序列和旧概率。
2. 环境判分，再用格式奖励等组成 total；同题组算相对优势，PPO 则算 token GAE。
3. 将固定经验拆开、缓存到 CPU，再随机拼成训练 batch。
4. 用当前 policy 对这些固定 token 重算可导概率，用优势加权相应算法目标。
5. 只在生成 token 上归约 loss，累积梯度后裁剪并用 Adam 更新。
6. 用新策略采集下一轮；数据耗尽结束，当前脚本不会自动保存模型。

最关键的理解是：**奖励和优势决定应该增加还是减少哪些生成 token 的概率；训练阶段的重新前向提供梯度；old/reference 是两个用途不同的固定比较对象。**
